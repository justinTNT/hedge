# Framework Plan

## Why

Hedge is a reusable framework: F# models → autogenerated web-code, plus a generic
runtime and a generic admin. `packages/hedge` is the framework; `apps/*` are apps
that share it. microblog is the **golden model** — reference implementation and test
fixture. The framework has held up across six apps: microblog (golden),
articles (justat/ndct), music (dont/just.saymay.be), pathname (static comic),
archive (ntne.ws, D1 + FTS5), basewatch (pages/menus, first module-shaped app).

## Structure

```
packages/hedge/
  src/Hedge/     Interface, Schema, SchemaCodec, Validate, Codec, Workers, OAuth,
                 Router, Admin (dispatcher + CRUD + AdminTable), EventHub, Events
  src/Admin/     Generic admin client (App.fs, RichText.fs) + admin.css baseline
  src/Gen/       Code generator (Program.fs) + Scaffold.fs (new-app template)

apps/<app>/
  src/Models/    Domain.fs, Api.fs, Ws.fs, Config.fs        ← authored
  src/Server/    Handlers.fs, AdminConfig.fs (~16 lines), Env.fs, Worker.fs,
                 generated/ (Db, AdminGen, Routes)          ← Handlers authored, rest generated/wiring
  src/Codecs/    generated/Codecs.fs
  src/Client/    App.fs, Api.fs, generated/ClientGen.fs     ← App authored
                 (+ GuestSession.fs, RichText.fs on comment/rich apps)
  lib/           guest-session.js, rich-text/ (per-app copies today — see app-lib)
  wrangler.toml  package.json  index.html  admin.html  vite.config.js
```

### Framework vs app boundary

Framework = the **models→web-code engine** + generic runtime + generic admin. NOT
"anything reused" (shared app views/features are *app-library*, below).

- **Framework** (`packages/hedge`): type system + `[<Table>]`, schema reflection,
  D1/R2/KV bindings, codec engine, router (incl. `/api/events` WS upgrade + `/blobs`),
  validation, `createWorker`, the generic admin (client + dispatcher + schema-driven
  CRUD + `AdminTable` + `admin.css` baseline), and the live-events transport
  (`EventHub` DO + `Events.broadcast`). Gen emits per-app plumbing from the models.
- **App**: `Domain.fs` (types → schema), `Api.fs` (endpoints), `Ws.fs` (event types),
  `Handlers.fs` (business logic), `Client/App.fs` (Elmish UI), `AdminConfig.fs`
  (wires the app's generated tables + admin-key check into the framework dispatcher),
  `Worker.fs` (~10 lines wiring `createWorker`). Everything else is generated.

**Developer focus** stays five files: `Domain.fs`, `Api.fs`, `Ws.fs`, `Handlers.fs`,
`Client/App.fs`.

## North star: apps as mountable modules; a site is a composition

Endgame: stop treating microblog / pages / articles / music as monolithic deploys.
Each becomes a self-contained **module** — `Domain` + `Api` + `Handlers` + a `Client`
component + its admin entities, exposing a mount point. A **site** = one deploy, one
D1, importing the modules it wants and mounting them under routes (e.g. an org-site
with the microblog mounted at `/blog`). "Make a new app by merging the microblog with
the org-site" is the motivating case.

hedge is most of the way there: Gen reflects over `Models` and emits combined
Db/Routes/Admin/Codecs; the Router dispatches; the generic admin lists whatever tables
exist. What the framework must add to compose cleanly (all in-boundary):
- **Route prefixing / mounting** in Router (a module's routes under a mount point).
- **Client-side module registry** so the shell renders the right module's component.
- **Table / type namespacing** so two modules' `comments` tables don't collide.
- Gen composing **multiple modules'** models into one schema/admin/codecs.

**Design this against the FIRST real merge (org-site + blog), not speculatively.**

## Done — framework consolidation shipped

The consolidation "warm-up" (byte-identical boilerplate → framework, behind a
build-all + `test.sh` net, deployed across the whole estate):

- **Generic admin → framework.** The 155-line CRUD dispatcher, the schema-driven CRUD
  handlers, and the `AdminTable` type all live in `Hedge.Admin`; each app's
  `AdminConfig.fs` is ~16 lines (`{ Tables; GetDb; CheckKey }`). Fixed a latent
  scaffold-drift bug (music's `genericUpdate` didn't bind `updated_at`).
- **Admin CSS baseline → framework.** `packages/hedge/src/Admin/admin.css`, a
  token-driven (`--admin-*`) baseline; apps re-skin via token overrides. microblog
  keeps its own rules as overrides; everyone else takes the baseline.
- **Live-events transport → framework.** `Hedge.EventHub` (the payload-agnostic
  broadcast DO) + `Hedge.Events.broadcast`. Class name kept `EventHub` → no DO
  migration. Consumers (comments today) declare an event type + one `broadcast` call.
- **Scaffold updated** so new apps emit all of the above — the drift can't return.
- **basewatch**: first module-shaped app (pages/menus), Feliz/Elmish client (first
  non-feed client), migrated onto the rich-text JSON pipeline.

## Remaining framework candidates (model→codegen / generic runtime — in boundary)

- **Per-tenant config.** Tenant identity is scattered/half-built: `SITE_SLUG`/`SITE_LOGO`
  injected ad hoc by `vite.config.js`; `Models.Config.GlobalConfig`/`FeatureFlags`
  defined but never wired to the client. Consolidate into ONE capability: the framework
  stamps `body.tenant-<slug>` and delivers a typed `{ slug; title; logo; features }` to
  the client via an accessor; apps just declare each tenant's values (wrangler `[env.*]`
  + build env stay app-level — the tenant *list*, not the mechanism). Then per-tenant
  behaviour gates on a `features` flag instead of the hardcoded
  `body.classList.contains('tenant-usbase')` check in `Client/Shared.fs` (already grown
  to a two-tenant list — the smell this removes).
- **Multi-param / query-string GET endpoints.** `Hedge.Interface` has only `Get` (no
  param) and `GetOne` (one path param), forcing the `tag~cursor` packing hack
  (microblog) and the section+search workarounds (archive). Add a two-param /
  query-string GET type + teach Gen to emit its route + client wrapper.
- **`features` capability system in Gen.** Apps/models declare capabilities (comments,
  guests, tags, search, admin); Gen emits only those. Kills the "scaffold everything,
  then strip" tax (archive was copy-articles-then-delete-the-comment-stack). This is the
  framework half of "modules"; the app half is the guest-comments library.
- **`[<Searchable>]` models → FTS.** Mark a model searchable; Gen emits the FTS5 virtual
  table + migration + `/api/search` endpoint + codec. Hand-rolled in archive today.
- **Image field type.** Add a semantic `Blob`/`Image` type to `Interface.fs` so a field
  typed that way is *generated* by Gen + the generic admin into an upload control wired
  to `/api/blobs` (models → web-code — that's what makes it framework). A bespoke upload
  button in a hand-written view stays app code. See `notes/IMAGES.md` (Workstream D);
  the other image workstreams are app/ETL work and can land independently.
- **(Parked) build/edge rich-text pre-render.** `RichContent` ships the full TipTap
  bundle to the *public* page (basewatch 140→480 KB). A build-time or edge JSON→HTML
  pre-render would keep the editor off read-heavy public pages. No consumer demands it
  yet — note only.

Deliberately staying app-level: **cursor pagination** — per-list SQL + cursor semantics
are app-specific, and the scroll helpers (`watchScroll`, `loadMoreIfSentinelVisible`)
are thin list-UI.

## App-library candidates (reused features/presentation — NOT framework)

- **`guest-comments`** — the identity/comment/attribution/OAuth-avatar stack
  (`Server/{Identity,Attribution}.fs`, comment bits of `Handlers`/`Sql`,
  `Client/GuestSession.fs`, `lib/guest-session.js`, comment UI), **plus its live layer
  as a *consumer* of the framework live-events transport** (`NewCommentEvent`,
  broadcast-on-create, client append). Copied byte-for-byte between microblog +
  articles; archive dropped it; music copied-but-unused. Extract as a **mountable
  module** — a pages app must be able to add it as a sub-section. This IS what
  microblog-as-a-module becomes.
- **`rich-text`** — `Client/RichText.fs` + `lib/rich-text/` (TipTap). **Rule-of-three
  confirmed** (microblog, articles, basewatch all carry a byte-copied `lib/rich-text/`).
  Single-source it. The editor's **extension set (`VIEWER_EXTENSIONS`) is the canonical
  content schema** — the editor, the JSON→HTML viewer (`renderRichTextHtml`), and any
  HTML→JSON converter must agree on it exactly, so it's the lib's center of gravity, not
  a detail buried in a per-app `tiptap-editor.js`. Two facts the lib must own:
  - **`RichContent` is a storage-format contract, not a display flag.** The field type
    (framework: Interface + Gen emit the `richContent` attr) *means* the column stores
    **ProseMirror JSON**. The type is framework; its meaning is app-lib — publish the
    contract. Adopting it on a field holding anything else (e.g. legacy HTML) is a
    **migration**, not a flag flip (the editor's `JSON.parse` fails silently → empty
    edit boxes; basewatch bug, fixed by migrating the 29 pages to JSON).
  - **HTML→JSON converter is reusable tooling** (here or in `etl`): the faithful recipe
    is **jsdom + `@tiptap/core` `generateJSON` against the shared extension set** (the
    real-browser parse path). NOT `@tiptap/html` — its zeed-dom doesn't parse inline
    `style`, silently dropping `text-align`/colour.
- **presentation helpers** — day-grouping, date formatting, teaser/HTML-entity
  extraction (archive `deriveTeaser`), feed/detail Elmish patterns, the nav-tree builder
  (flat menu → tree, basewatch `App.fs navTree`).
- **`etl` tools** — mongo→D1 pipeline (bson parse, de-mojibake, chunked seeding,
  cover/URL derivation), plus two rule-of-three-confirmed steps:
  - **asset-mirror pass** (justat, basewatch, ndct): scan migrated content bodies for
    external asset refs (dead/moved hosts: `larak.in`, `saymay.be`, Ghost
    `/content/images/…`, Netlify), download each, upload to the app's R2 bucket, rewrite
    body paths to `/blobs/<key>` (served by the framework `/blobs/` route).
  - **verify step**: after mirroring, fetch every referenced asset and assert its
    `content-type` — the SPA fallback hides 404s (see learnings).

## Sequencing & discipline

- **Next consolidation:** extract `guest-comments` as a mountable module (its live layer
  consuming the framework transport), migrate the live apps onto it, prune music's
  vestigial scaffold copies. Then the codegen work — `features` + `[<Searchable>]` —
  now informed by three-plus apps.
- **Design the mount/compose runtime against the first real merge**, not in the abstract.
- **Rule of three**: don't promote an abstraction until a third app has voted.
- **Golden-model test** (still open): `test.sh` does build verification only. Add
  diffing generated files against checked-in expected output — and **cover the scaffold's
  template strings** (`Gen/Scaffold.fs`), not just generated files. The music admin-CRUD
  bug was exactly this gap: a golden-model fix never back-ported into the scaffold
  template, invisible because both compiled. Better still, keep shrinking templates by
  pushing their bodies into the framework (as done for Admin), which removes the drift
  class entirely.
- **Never rewire the live apps under build pressure.**

## Operational learnings

- **The SPA fallback silently masks missing assets.** With
  `not_found_handling = "single-page-application"`, a missing `/x.webp` returns
  `index.html` — `200 text/html`, not `404`. A broken asset *looks present*. **Status
  codes lie under an SPA fallback; verify `content-type`.** (Hid the ndct
  missing-images bug until after cutover; motivates the ETL verify step.)
- **R2 + `/blobs/<key>` is the settled content-asset home** (justat, ndct). Content
  images migrated off dead hosts land in the app's R2 bucket, served by the framework
  `/blobs/` route (content-type from the key extension when R2 httpMetadata is absent).
  Removing external refs also cuts a Netlify dependency each time.

## Prune (batch into the consolidation)

- music's vestigial `GuestSession.fs`/`RichText.fs`/`Ws.fs` (scaffold copies, unused —
  music has no comments). `EventHub.fs` is already gone from apps (now framework); once
  guest-comments is a module, music simply won't import any of it.
